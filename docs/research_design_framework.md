# LLM 驱动的消费者洞察研究框架

## 设计文档 v0.1

---

## 1. 核心问题

**一个创业者或产品经理提出一个问题，系统如何从问题出发，自动生成研究设计，最终输出可操作的消费者洞察？**

传统用户研究的核心挑战在于：

- 问卷、访谈成本高、周期长，且样本往往不覆盖极端情形
- 研究者需要事先知道"要问什么"（变量选择依赖经验）
- 样本分布受真实世界偏差影响（愿意接受访谈的用户本身就是偏样本）
- 从数据到洞察的路径不透明

本框架用 LLM + 合成 persona 替代上述流程，构造一个从**自然语言问题**到**可解释消费者洞察**的完整链路。

---

## 2. 框架全景

```
┌─────────────────────────────────────────────────────────────────┐
│  Step 0：问题理解                                               │
│  输入：自然语言问题                                             │
│  输出：X（场景上下文）+ Y（目标变量定义）                       │
└──────────────┬──────────────────────────────────────────────────┘
               │
               ▼
┌─────────────────────────────────────────────────────────────────┐
│  Step 1：研究轴生成                                             │
│  输入：X 场景描述                                               │
│  输出：D 个正交的消费者描述维度（多样性轴）                     │

│  目标：在 D 维空间里均匀覆盖，确保 Y 的分布尽量宽且均匀        │

               ▼

│  Step 3：Y 值评估                                               │
│  对每个 persona，用 LLM 基于 TPB 推导 Y 的预测值               │

               ▼

│  目标：识别哪些消费者特征驱动 Y 的变化                          │
│  输出：特征重要性排序 + 分群画像 + 可操作建议                   │
└─────────────────────────────────────────────────────────────────┘
```

## 3. 各步骤详解

### Step 0：问题理解（X 和 Y 的识别）

用户输入一个自然语言问题，例如：

> "我想知道哪类用户最可能接受一款面向中年男性的冥想 App"
> "我们的 AI 写作助手为什么在独立创作者中打不开局面"
> "新能源汽车在三四线城市的采纳阻力主要来自哪里"

LLM 需要从问题中抽取：

| 输出项 | 含义 | 示例 |
|--------|------|------|
| **X（场景）** | 产品/服务描述 + 目标用户范围 + 当前语境 | "面向中年男性、主打睡眠改善的冥想 App，在一二线城市推广初期" |
| **Y（目标变量）** | 要预测/解释的消费者行为或态度 | "下载后连续使用 7 天的意愿"（而非宽泛的"接受度"） |
| **Y 的方向** | Y 值高/低分别意味着什么 | 高 = 强留存意愿，低 = 下载即卸载 |
| **研究目的** | 是"找目标人群"还是"找阻力来源"还是"比较方案" | 找阻力来源 |

**关键设计原则：Y 必须是可操作的行为/态度，而非模糊的情感评价。**

---

### Step 1：研究轴生成

给定 X 场景，LLM 生成 D 个正交的**消费者描述维度**，这些维度是后续 persona 生成的坐标系。

**维度的要求：**
- **与 Y 在理论上相关**（否则采样空间无效）
- **与 Y 保持输入/输出分离**（不能直接包含 Y 的内容，避免循环自证）
- **互相正交**（低相关，确保采样空间真正多维）
- **可被具体化成 persona 文本**（LLM 能基于维度值生成有血有肉的用户描述）

**通用骨架（可跨场景复用）：**

| 通用维度 | 在不同场景下的实例化 |
|----------|---------------------|
| 痛点意识度 | "有多清楚自己睡眠不好" / "有多意识到写作效率低" |
| 现有方案依赖深度 | "多依赖褪黑素/助眠药" / "多依赖 Word + ChatGPT 手动组合" |
| 新产品接受度 | "尝试新 App 的积极性" / "对 AI 工具的开放程度" |
| 外部约束强度 | "工作强度、时间碎片化程度" / "预算限制" |
| 付费心智 | "为健康类工具付费的历史" / "为生产力工具付费的意愿" |
| 问题归因方式 | "认为睡眠问题该靠自己解决还是医生介入" |

LLM 会根据 X 裁剪这套框架，增删特定场景下更重要的维度。

---

### Step 2：Persona 生成（均匀采样是核心）

**为什么要均匀采样，而非模拟真实分布？**

真实用户分布往往集中在某几个区间（如大多数人痛点意识度居中），如果按真实分布采样，极端情形的 persona 会稀少甚至缺失。而极端情形恰恰是洞察的来源：

- 是什么让极高痛点意识度的用户仍然不采纳？
- 是什么让外部约束极强的用户反而转化了？

因此：**采样目标是覆盖 Y 的完整分布，而非重现真实人口分布。**

**具体做法：**

1. 每个维度取值范围定义为 [0, 1]（低 → 高）
2. 用 Sobol 序列在 D 维空间里生成 N 个均匀分布的点（低差异采样）
3. 每个点 → LLM 生成对应的 persona 文本（有姓名、职业、日常场景、具体态度描述）
4. 验证生成结果：确认 persona 的文本内容与维度数值一致

**N 的选择：**
- 快速探索：N = 50（约 2-3 小时 LLM 调用）
- 标准研究：N = 200
- 高精度：N = 500+

---

### Step 3：Y 值评估

对每个 persona，LLM 扮演"该 persona 本人"，基于 TPB 框架评估 Y。

**TPB 评估结构：**

```
对 Persona P 评估 Y（7 天持续使用冥想 App 的意愿）：

1. 态度（Attitude）
   - 对冥想 App 的认知评价：有用吗？适合我吗？
   - 对使用体验的情感预期：会喜欢吗？会坚持吗？
   → A = [0, 1]

2. 社会规范（Social Norm）
   - 重要他人（伴侣、朋友、同事）怎么看待我用冥想 App？
   - 周围人有在用吗？有人推荐过吗？
   → SN = [0, 1]

3. 感知行为控制（PBC）
   - 我有时间每天打开 App 吗？
   - 我有能力坚持下去吗？冥想对我来说难吗？
   → PBC = [0, 1]

4. 行为意向
   I = w_A * A + w_SN * SN + w_PBC * PBC
   → I ∈ [0, 1]

5. 摩擦调整
   - 竞争性习惯（已有助眠方案的用户切换成本）
   - 外部障碍（时间、价格）
   → Y_final = f(I, friction)
```

**输出格式（结构化，每个 persona 一条记录）：**

```json
{
  "persona_id": "P_042",
  "dimensions": {
    "pain_awareness": 0.8,
    "current_solution_dependency": 0.3,
    "openness_to_new": 0.6,
    "external_constraints": 0.7,
    "payment_mindset": 0.5,
    "self_attribution": 0.4
  },
  "tpb_scores": {
    "attitude": 0.72,
    "social_norm": 0.45,
    "pbc": 0.38,
    "intention": 0.56
  },
  "friction": 0.25,
  "Y": 0.49,
  "reasoning_summary": "..."
}
```

### Step 4：数据分析 → 洞察

有了 N 条 persona 记录（每条含 D 个维度值 + Y），这就是一个标准的**特征重要性**问题。

**分析目标：哪些消费者特征驱动 Y 的变化？**

**分析手段：**

| 方法 | 用途 | 输出 |
|------|------|------|
| 相关分析 | 哪个维度与 Y 线性相关最强 | 相关系数排序 |
| 随机森林 / XGBoost | 非线性关系 + 交互效应 | Feature importance |
| SHAP 值 | 每个维度对每个 persona 的 Y 贡献解释 | 局部解释 + 全局排序 |
| 聚类分析 | 按 Y 值区间划分 persona 群，看群内特征共性 | 细分画像 |
| 边界分析 | 找 Y 从低到高的"翻转条件" | 临界值识别 |

**典型洞察输出示例：**

```
驱动 Y（7天留存意愿）的主要因素（按重要性排序）：

1. 感知行为控制（PBC）是最强预测因子（SHAP = 0.31）
   → 核心阻力不是"不想用"，而是"觉得自己坚持不了"
   → 建议：产品侧增加进度感知 + 最小化每日承诺（3分钟即可）

2. 现有方案依赖深度 × 痛点意识度 的交互效应显著
   → "知道自己有问题但已经有固定应对方式"的用户 Y 最低
   → 建议：针对这类用户设计"比较试验"引导（"试试和你现在做法的区别"）

3. 社会规范的影响在高外部约束用户中显著放大
   → 伴侣/朋友推荐 > 任何广告渠道（这类用户没时间主动搜索）
   → 建议：设计口碑传播机制（分享打卡 + 邀请伴侣一起）
```

## 4. 为什么均匀分布在 Y 上很关键

这是整个框架最核心的设计决策，值得单独解释。

**如果 Y 分布不均匀会怎样？**

假设 N=200 个 persona 中有 170 个 Y 值在 0.6-0.9 之间（高意愿区间），只有 30 个 Y < 0.4：

- 特征重要性分析会被高意愿群体主导
- 低意愿用户（潜在的"阻力群体"）样本不足，无法识别其驱动因素
- 无法识别 Y 从高到低的"临界翻转条件"

**均匀分布的目标：**

```
Y 的分布目标（N=200）：

[0.0, 0.2)  约 40 个 persona  ← 强阻力群体
[0.2, 0.4)  约 40 个 persona  ← 中阻力群体
[0.4, 0.6)  约 40 个 persona  ← 中性群体
[0.6, 0.8)  约 40 个 persona  ← 初步接受群体
[0.8, 1.0]  约 40 个 persona  ← 强采纳群体
```

**如何在输入端保证 Y 的输出均匀？**

1. 在多样性轴空间里均匀采样（Sobol 序列）是必要条件但不充分
2. 需要验证：生成的 N 个 persona 的 Y 分布是否覆盖完整区间
3. 如果某区间 Y 值稀少，可以**定向补充**：固定某些驱动因素为极端值，补充生成对应区间的 persona
4. 最终数据集的分析权重可以加权调整，以抵消 Y 分布不均的影响

## 5. 与其他模块的关系

```
本框架（研究设计）
    │
    ├── 使用 → syn_persona.md（具体的 persona 生成协议）
    │              ↓
    │         persona 文本 + 维度数值
    │
    ├── 使用 → TPB 决策模型（评估 Y）
    │              ↓
    │         Y 值 + 分项评分
    │
    └── 输出 → 洞察报告
                   ↓
              创始人评估框架（解读结论含义）
```

**本框架解决的是"研究设计"层的问题**——什么问题值得问、测什么变量、怎么采样——而不是具体的技术实现。

## 6. 适用场景与局限

### 适用场景

| 场景 | 典型问题 | 适合原因 |
|------|----------|----------|
| 创业早期验证 | "谁会买单？谁不会？为什么？" | 无真实用户，合成 persona 是最低成本的代理 |
| 产品功能决策 | "这个新功能对哪类用户最有价值？" | 快速生成分层用户反馈 |
| 营销策略设计 | "不同渠道对哪类用户有效？" | 可以枚举场景变量（渠道 × 用户特征） |
| 政策设计研究 | "政策对哪类群体的影响最大？" | 可系统覆盖边缘群体 |

### 局限与边界

| 局限 | 说明 | 应对 |
|------|------|------|
| LLM 的内部偏见 | LLM 对某些人群的行为预测可能有系统性偏差 | 用真实用户数据校验高置信 persona 的 Y 值 |
| Y 的可预测性 | 如果 Y 强依赖真实世界外部因素（政策变动、竞品行为），LLM 无法预测 | 明确框架边界，这类问题不适合此框架 |
| 维度覆盖的完整性 | 如果 Step 1 遗漏了关键维度，后续分析会系统性错误 | 由领域专家审查维度列表 |
| 洞察的可迁移性 | 合成数据的洞察需要真实验证才能推广 | 将高优先级结论设计为 A/B 测试验证 |

---

## 7. 进化方向

**v0.1（当前）：手动定义维度，LLM 生成 persona + 评估 Y**

**v0.2：** LLM 自动生成维度，人工审查后确认

**v0.3：** 加入验证环节——用少量真实用户数据校准 LLM 的 Y 预测偏差

**v1.0：** 闭环系统——
1. 自然语言问题 → 自动识别 X + Y
2. 自动生成维度 → 自动采样 + persona 生成
3. 自动评估 Y → 自动分析 → 生成洞察报告
4. 报告中标注每条结论的置信度 + 推荐验证方式
